# Контракт: HTTP API и бинарный таймлайн

Единый источник правды между движком и браузером. Любое изменение — отдельным явным коммитом: правка этого файла, golden-тестов в `tests/contract/` и перечень того, что поправить в веб-клиенте.

Статус: **черновик v1**. Протокол v0 (поток кадров по WebSocket, uniform'ы шейдеров, control-сообщения) удалён целиком, он остался в истории git.

Схема работы:

1. Браузер загружает файл: `POST /tracks` → `202 {track_id}`. Движок анализирует трек в фоне.
2. Браузер следит за анализом через SSE: `GET /tracks/{track_id}/events`. Последнее событие — `ready` с метаданными трека или `failed` с ошибкой.
3. Браузер скачивает таймлайн: `GET /tracks/{track_id}/timeline`. Звук он играет сам и ищет признаки по `audio.currentTime`.

Аудиофайл сервер обратно не отдаёт. Раскладку таймлайна закрепляют golden-тесты в `tests/contract/`.

## 1. `GET /health` и `GET /ready`

`GET /health` — `200`, `application/json`:

```json
{ "ok": true, "protocol": 1 }
```

`protocol` — версия протокола из этого документа, сейчас `1`. Клиент сверяет её до загрузки трека. Ответ значит только то, что процесс движка жив.

`GET /ready` — для балансировщика и проверок при деплое, браузер его не вызывает. `200`, `application/json`:

```json
{ "ok": true }
```

означает, что движок может принимать загрузки: в серверном режиме отвечают все хранилища (Postgres, Redis, S3). Если хотя бы одно не ответило — `503 unavailable` (раздел 7), в `message` перечислены те, что не ответили.

## 2. `POST /tracks`

Запрос: `multipart/form-data`, одна часть `file` с аудиофайлом. Поддерживаются mp3, wav, flac и ogg. Формат определяется по содержимому файла, расширение и `Content-Type` части не учитываются.

Успех: `202`, `application/json`:

```json
{ "track_id": "9f2c41d07a3b55e1" }
```

`track_id` — непрозрачный идентификатор; клиент его не разбирает, только подставляет в URL. Одинаковые по содержимому файлы получают один и тот же `track_id`: если такой трек уже разобран, анализ не повторяется и события сразу сообщают `ready`. Неудачный анализ не запоминается: повторная загрузка того же файла запускает его заново.

Сервер хранит ограниченное число треков. Вытесненный трек отвечает `404 track_not_found`, клиент загружает файл заново.

Сервер ограничивает число загрузок за последний час: с одного адреса (IPv4 или сеть IPv6 /64), с сети IPv6 /48 и со всего мира вместе; все три лимита — настройки сервера. Сверх любого из них — `429 rate_limited` с заголовком `Retry-After`: через сколько секунд можно загружать снова. Тело запроса при этом не читается. Считается каждая попытка, в том числе повторная загрузка уже разобранного файла и отклонённая как битая; не считается только загрузка, отклонённая с `503 busy`, потому что её клиент повторяет по просьбе сервера.

Одновременно сервер принимает ограниченное число загрузок (настройки сервера): с одного адреса и с одной сети IPv6 /48 — сверх них `429 rate_limited` с `Retry-After`, на весь сервер — сверх него `503 busy`. Оба ответа приходят сразу, без очереди, и не тратят часовой лимит. Тело должно приходить не медленнее минимальной скорости, без долгих пауз и целиком за ограниченное время (настройки сервера), иначе сервер обрывает загрузку с `400 no_file`.

Сервер принимает звук до 8 каналов с частотой дискретизации до 192 кГц, иначе — `415 unsupported_format`. Кроме размера файла и длительности ограничен объём декодированного звука — длительность × частота × число каналов (настройка сервера), сверх него — `413 file_too_large`.

Синхронные ошибки этого запроса: `no_file`, `file_too_large`, `unsupported_format`, `rate_limited`, `busy` (раздел 7). Ошибки декодирования и анализа приходят позже, событием `failed`.

## 3. `GET /tracks/{track_id}/events`

Server-Sent Events, `200`, `text/event-stream`. Сразу после подключения сервер присылает текущее состояние трека, дальше — каждое изменение. События трёх типов, `data` всегда одна строка JSON.

```
event: progress
data: {"stage": "tempo", "progress": 0.55}

event: ready
data: {"track_id": "9f2c41d07a3b55e1", "duration_s": 432.17, ...}

event: failed
data: {"error": "undecodable", "message": "..."}
```

- **`progress`** — `stage` одно из `decoding`, `spectrum`, `tempo`, `structure` (в этом порядке); `progress` — доля всего анализа, 0..1, между событиями не убывает.
- **`ready`** — анализ закончен; `data` — тот же объект, что отдаёт `GET /tracks/{track_id}` (раздел 4).
- **`failed`** — анализ не удался; `data` — тело ошибки (раздел 7), `error` одно из `undecodable`, `analysis_failed`, `internal`.

После `ready` или `failed` сервер закрывает поток. Клиент, получив одно из них, сам закрывает `EventSource`, иначе браузер переподключится. Переподключение безопасно: сервер снова пришлёт текущее состояние. Поля `id` и заголовок `Last-Event-ID` не используются. Строки-комментарии (`:` в начале) клиент игнорирует, `EventSource` делает это сам.

Неизвестный `track_id` — обычный JSON-ответ `404 track_not_found`, а не поток.

Число одновременных потоков ограничено: с одного адреса и с одной сети IPv6 /48 — `429 rate_limited`, на весь сервер — `503 busy`; оба приходят обычным JSON-ответом, а не потоком. Поток живёт не дольше нескольких минут (настройка сервера): потом сервер закрывает его без `ready` и `failed`, браузер переподключается и снова получает текущее состояние.

## 4. `GET /tracks/{track_id}`

`200`, `application/json` — метаданные разобранного трека:

```json
{
  "track_id": "9f2c41d07a3b55e1",
  "duration_s": 432.17,
  "bpm": 128.0,
  "beat_offset_s": 0.312,
  "sections": [
    { "name": "intro",     "start_s": 0.0,    "end_s": 60.3,   "loud": false },
    { "name": "buildup",   "start_s": 60.3,   "end_s": 90.3,   "loud": false },
    { "name": "drop",      "start_s": 90.3,   "end_s": 210.3,  "loud": true  },
    { "name": "breakdown", "start_s": 210.3,  "end_s": 270.3,  "loud": false },
    { "name": "drop",      "start_s": 270.3,  "end_s": 390.3,  "loud": true  },
    { "name": "outro",     "start_s": 390.3,  "end_s": 432.17, "loud": false }
  ]
}
```

| Поле | Тип | Значение |
|---|---|---|
| `track_id` | string | тот же, что в URL |
| `duration_s` | number | длительность декодированного звука, с, > 0 |
| `bpm` | number | темп трека, 20..300; сетка постоянная, один темп на весь трек |
| `beat_offset_s` | number | якорь сетки тактов — время начала такта 0, с; `0 ≤ beat_offset_s < bar_duration_s` |
| `sections` | array | части трека, хотя бы одна |
| `sections[].name` | string | одно из `intro`, `buildup`, `drop`, `breakdown`, `outro`; имена могут повторяться |
| `sections[].start_s`, `end_s` | number | границы части, с, `start_s < end_s` |
| `sections[].loud` | boolean | громкая часть (на полосе трека рисуется светлее) |

Здесь и дальше `beat_duration_s = 60 / bpm`, `bar_duration_s = 4 · beat_duration_s`: в такте 4 доли.

`beat_offset_s` — не обязательно первая слышимая сильная доля. Сетка тактов продолжается на весь трек, и если трек начинается с тишины, первая сильная доля музыки придётся на такт 1 или позже. Сильные доли всегда лежат в моменты `beat_offset_s + k · bar_duration_s`.

Части идут по времени без пропусков и наложений: первая начинается в `0`, каждая следующая начинается там, где кончилась предыдущая, последняя кончается в `duration_s`.

Пока анализ идёт — `409 not_ready`. Если анализ не удался — та же ошибка, что пришла в событии `failed`. Неизвестный трек — `404 track_not_found`.

## 5. `GET /tracks/{track_id}/timeline`

Успех: `200`, `application/octet-stream`, `Cache-Control: private, max-age=3600`: таймлайн не меняется, пока трек хранится. Все числа little-endian. Ошибки — как у `GET /tracks/{track_id}`, и ещё `429 rate_limited`, если этому адресу или его сети уже отдаётся слишком много таймлайнов, и `503 busy`, если их слишком много на весь сервер.

### Заголовок, 16 байт

| Смещение | Тип | Поле | Значение |
|---|---|---|---|
| 0 | uint32 | `version` | версия протокола, сейчас `1`; таймлайн с другой версией клиент не читает |
| 4 | float32 | `frame_rate_hz` | кадров в секунду, > 0 и конечное |
| 8 | uint32 | `frame_count` | число кадров `F`, ≥ 1 |
| 12 | uint32 | `bar_count` | число тактов `B`, ≥ 1 |

Движок анализирует звук на частоте 44 100 Гц с шагом STFT 512 сэмплов, поэтому `frame_rate_hz = 44100 / 512 = 86,1328125` (в float32 хранится точно). Клиент всё равно берёт частоту из заголовка и не подставляет константу.

### Массивы

Сразу за заголовком идут четыре плотных массива, ровно в этом порядке, построчно (row-major). Первым идёт единственный float32-массив, поэтому он выровнен на 4 байта и клиент читает его через `Float32Array` прямо поверх буфера; остальные массивы uint8 и выравнивания не требуют.

| # | Массив | Форма | Тип | Смещение |
|---|---|---|---|---|
| 1 | `peaks` | B × 8 × 2 | float32 | `16` |
| 2 | `bands` | F × 64 | uint8 | `16 + 64·B` |
| 3 | `levels` | F × 5 | uint8 | `16 + 64·B + 64·F` |
| 4 | `fourier` | B × 200 | uint8 | `16 + 64·B + 69·F` |

Длина ответа ровно `16 + 264·B + 69·F` байт; при другой длине клиент таймлайн не читает.

- **`peaks`** — до 8 главных частот такта, по строке на частоту: `freq_hz`, `amp`. Это вершины (локальные максимумы) спектра `fourier` того же такта: `freq_hz` в 30..600, `amp` в той же шкале 0..1, что и `fourier`. Строки по убыванию `amp`. Если частот меньше 8, в конце идут строки из одних нулей; `freq_hz = 0` означает пустую строку, после пустой строки непустых нет. Фазы нет: у усреднённого за такт модуля спектра её не существует, начальные фазы эпициклов выбирает клиент.
- **`bands`** — 64 лог-полосы. Центр полосы `i` (0..63): `30 · (16000 / 30)^(i / 63)` Гц, от 30 Гц до 16 кГц. Значение — уровень полосы 0..1; как он получен (дБ-шкала, нормировка, сглаживание), решает движок, клиент рисует как есть.
- **`levels`** — 5 столбцов строго в порядке `kick`, `bass`, `mid`, `high`, `energy`. Каждый 0..1. `kick` — огибающая кика, `bass`, `mid`, `high` — уровни диапазонов, `energy` — медленная энергия за несколько тактов.
- **`fourier`** — модуль спектра |X(f)|, усреднённый за весь такт, 200 бинов. Центр бина `j` (0..199): `30 · (600 / 30)^(j / 199)` Гц, логарифмически от 30 до 600 Гц. Значения линейные (не дБ) и нормированы на максимум по всему треку, а не по такту: тихие такты остаются тихими, тишина даёт нули. Растянуть такт под экран клиент может сам.

### Число кадров и тактов

Движок считает их так (клиент их не пересчитывает, а берёт из заголовка):

- `F = ceil(duration_s · frame_rate_hz)`, то есть число шагов STFT по декодированному звуку. Кадр `i` описывает момент `i / frame_rate_hz` — центр окна STFT.
- `B = max(1, ceil((duration_s − beat_offset_s) / bar_duration_s))`. Такт `k` начинается в `beat_offset_s + k · bar_duration_s`; последний такт может выходить за конец трека.

### Квантование uint8

Все массивы uint8 хранят значения 0..1:

```
q = floor(clamp(x, 0, 1) · 255 + 0.5)      кодирование
x = q / 255                                 декодирование
```

`0` переходит в `0`, `1` — в `255`, ошибка не больше `1/510`.

## 6. Поиск по времени

`t = audio.currentTime`, с.

- Кадр: `i = clamp(floor(t · frame_rate_hz), 0, F − 1)`.
- Доля: `n = floor((t − beat_offset_s) / beat_duration_s)` — номер доли, может быть отрицательным до `beat_offset_s`.
- Доля в такте: `beat_in_bar = n mod 4`, модуль через floor, всегда 0..3. Фаза доли: `(t − beat_offset_s) / beat_duration_s − n`, 0 ≤ фаза < 1.
- Такт: `k = clamp(floor(n / 4), 0, B − 1)`. До `beat_offset_s` такт прижимается к 0, а доля и фаза продолжают сетку назад.

Волны (waveform) в таймлайне нет: браузер берёт сигнал из `AnalyserNode` сам.

## 7. Ошибки

Все ошибки API приходят одним телом, `application/json`:

```json
{ "error": "unsupported_format", "message": "expected mp3, wav, flac or ogg" }
```

`error` — код из таблицы, клиент ветвится только по нему. `message` — текст для лога, клиент его не разбирает и не показывает как есть.

| HTTP | `error` | Когда |
|---|---|---|
| 400 | `no_file` | в запросе нет части `file`, она пустая или приходила слишком медленно |
| 413 | `file_too_large` | файл больше лимита по размеру, по длительности звука или по объёму декодированного звука; лимиты — настройки сервера |
| 415 | `unsupported_format` | содержимое не mp3, не wav, не flac и не ogg, или в звуке больше 8 каналов, или частота дискретизации выше 192 кГц |
| 422 | `undecodable` | формат распознан, но файл не декодируется (битый, обрезанный) |
| 422 | `analysis_failed` | звук декодирован, но анализ не дал результата (тишина, слишком короткий трек) |
| 404 | `track_not_found` | неизвестный или вытесненный `track_id` |
| 409 | `not_ready` | анализ трека ещё идёт |
| 429 | `rate_limited` | слишком много загрузок с этого адреса, его сети или со всего мира за час, либо слишком много одновременных загрузок, потоков событий или таймлайнов с этого адреса или его сети; заголовок `Retry-After` — через сколько секунд повторить |
| 503 | `busy` | сервер занят: очередь анализа заполнена, идёт слишком много загрузок, открыто слишком много потоков событий или отдаётся слишком много таймлайнов; клиент повторяет позже |
| 503 | `unavailable` | только `GET /ready`: хранилище движка не отвечает |
| 500 | `internal` | любая другая ошибка сервера |

## 8. Размер

Трек 7 минут при 86,13 кадра/с и 128 BPM: около 36 200 кадров × 69 байт ≈ 2,5 МБ плюс 224 такта × 264 байта ≈ 59 КБ.

## 9. Что меняется в веб-клиенте

Веб-клиент в `web/` реализует эту версию протокола. Перед каждой загрузкой он сверяет `protocol` из `GET /health` и при расхождении просит обновить страницу; его декодер таймлайна проверяется тем же golden-файлом `tests/contract/golden/timeline_v1.bin`, что и движок. `GET /ready` клиент не вызывает и `unavailable` от сервера не получает: этим кодом он сам помечает недоступный движок — сетевую ошибку и ответ прокси 502–504 без тела ошибки. На `429 rate_limited` клиент показывает, через сколько можно загрузить снова, по `Retry-After`; `busy` — что сервер занят.

Поток событий, закрытый сервером без `ready` и `failed`, `EventSource` переподключает сам. Отказ в потоке (`429` или `503`) он не переподключает, а при пропавшей сети переподключается бесконечно, поэтому клиент делает так: когда поток закрылся без `ready` и `failed` или пять раз подряд оборвался без единого события, клиент спрашивает `GET /tracks/{track_id}`; `200` — трек готов, `409 not_ready` — через несколько секунд открывает поток заново, любая другая ошибка, в том числе недоступный движок, — загрузка не удалась с этой ошибкой.
